# 1. 개발기술 개요 및 필요성

## 1-1. 개발 대상 기술 정의

### 1-1-1. 한 줄 정의

> **"AI가 웹에서 발굴한 한국 공급사 후보를, 대한민국 정부의 인허가 공공데이터 원장에 실시간으로 교차대조하여 (a) 진짜 제조사인지 중개상·브랜드사인지 판별하고 (b) 현재 폐업·휴업 상태가 아닌지 확인하는 신뢰검증 레이어(Trust-Verification Layer)."**

### 1-1-2. 기술의 구조 — 발굴과 검증의 분리

본 기술의 핵심은 **"발굴(Discovery)"과 "검증(Verification)"을 구조적으로 분리**하고, 검증 단계에 **정부 원장이라는 외부 진실 기준(external ground truth)** 을 강제 개입시키는 데 있다.

```
[1단계: 발굴 — AI (LLM + 웹 그라운딩)]
   해외 바이어 요구조건(카테고리/MOQ/인증/리드타임) 입력
        ↓
   생성형 AI가 웹에서 한국 공급사 후보군 생성
        ↓
   ※ 이 단계의 출력은 "가설"이며, 신뢰할 수 없다 (환각 가능)
        ↓
──────────────────  [ 검증 게이트 (본 과제의 R&D 대상) ]  ──────────────────
        ↓
[2단계: 대조 — 정부 공공데이터 원장]
   ├─ 식약처 화장품 등록업체 원장 → 화장품제조(공장) vs 화장품책임판매(브랜드) 판별
   ├─ 식약처 CGMP 적합업체 원장 → GMP 인증 여부 (사업자번호 매칭)
   ├─ HACCP 인증 식품제조사 원장 → 식품 안전 인증 여부
   ├─ 의료기기 제조/수입업체 원장 → 제조 vs 수입 판별
   ├─ 건강기능식품 업소 원장
   ├─ 의약외품 업체 원장
   └─ 국세청 사업자 상태 API (실시간) → 계속사업자 / 휴업 / 폐업
        ↓
[3단계: 판정]
   ├─ 원장 대조 성공 + 제조업 등록 확인 + 계속사업자  → 검증 배지 부여
   ├─ 원장에 제조업 등록 없음                          → 배지 거부 (중개상/브랜드 표시)
   ├─ 폐업·휴업 확인                                   → 경고 표시
   └─ 대조 가능한 정부 원장이 존재하지 않는 카테고리     → "검증 불가" 명시 (예: 의류)
        ↓
[4단계: 산출]
   신뢰 점수 · 위험 신호(red flag) · 영문 RFQ 초안 · PDF/CSV 리포트
```

### 1-1-3. 기존 접근과의 결정적 차이

| 구분 | 일반적 접근 | 본 기술 |
|---|---|---|
| AI 출력의 지위 | **최종 답변** | **검증 대상 가설** |
| 신뢰의 원천 | LLM의 학습 데이터 / 웹 평판 | **정부 인허가 원장 (법적 등록 사실)** |
| 환각 처리 | 사후 사용자 판단에 위임 | **구조적 차단** (원장 대조 실패 시 배지 거부) |
| 검증 불가 영역 | 얼버무림 / 그럴듯하게 서술 | **"검증 불가"를 명시적으로 출력** |

> ⚠ **표현의 정확성**: 본 기술에서 **공급사 후보의 "발굴"은 AI(웹 그라운딩)** 이고, **"대조·검증"이 정부 API**이다. "정부 API로 공급사를 발굴한다"는 서술은 사실이 아니므로 본 문서 어디에서도 사용하지 않는다.

### 1-1-4. 사업 경계 (Scope Boundary)

본 기술·서비스는 **리서치 도구(Research Tool)** 이다. 아래는 **명시적으로 사업 범위 밖**이다.

- 소싱 대행업 (거래 중개·수수료 수취) — ✕
- 감사·인증 기관 (제3자 인증서 발급) — ✕

이 경계를 넘는 순간 무역·물류·인증 관련 규제 및 거래 책임이 발생하므로, R&D 과제 범위 역시 **정보 제공·검증 레이어**에 한정한다.

## 1-2. 기술개발의 필요성

### 1-2-1. 시장 필요성 — "한국 공급사를 처음 찾는 해외 소규모 바이어"의 폭증

| 지표 | 수치 | 출처 |
|---|---|---|
| 2025년 한국 화장품 수출액 | **114억 달러** (전년비 +12.3%, **역대 최대**) | 식약처 발표 |
| 세계 순위 | **2위** (1위 프랑스 243억달러, 3위 미국 108억달러) | 식약처 |
| 화장품 무역흑자 | **101억 달러** (사상 첫 100억 달러 돌파) | 식약처 |
| 2025년 화장품 생산액 | **17조 9,382억원** (역대 최고) | 식약처 |
| **중소기업 화장품 수출 비중** | **69.8%** (2025 상반기 / 5년 전 약 55%) | 관련 통계 보도 |

**해석 (과장 없이):**

한국 화장품 수출은 사상 최대치를 기록했고, 그 성장의 **약 70%를 중소·인디 브랜드가 견인**하고 있다. 이는 두 가지를 동시에 의미한다.

1. **공급 측**: 해외에 이름이 알려지지 않은 **한국 중소 제조사(OEM/ODM)** 의 수가 많고, 이들은 영문 웹 노출·해외 마케팅 역량이 취약하다.
2. **수요 측**: **소량·저MOQ로 한국 공급사를 처음 찾는 해외 소규모 바이어**(인디 뷰티 브랜드 창업자, Amazon FBA 셀러, 소규모 수입사)의 절대수가 빠르게 늘고 있다.

즉, **"찾는 쪽도 초보이고, 찾히는 쪽도 무명"** 인 상태에서 양측이 만나야 하는 구조적 정보 비대칭이 발생하고 있다. 이 비대칭을 현재 메우고 있는 것이 **소싱 에이전시(중개상)** 이며, 바이어는 자신이 공장과 직접 거래하는지 중개상과 거래하는지조차 판별하지 못한다.

> ※ TAM/SAM/SOM 정량 산정은 위 통계에서 논리적으로 도출 가능한 범위를 넘어서므로, **검증된 출처 확보 후 기입**한다. 【확보 필요 — 출처 있는 시장규모 통계】

### 1-2-2. 기술적 필요성 — AI 검색 결과의 신뢰성 부재 (실증 근거)

생성형 AI에게 "한국의 저MOQ 화장품 공장을 찾아달라"고 하면, AI는 **그럴듯한 목록을 즉시 출력**한다. 문제는 그 목록의 **사실성을 검증할 구조가 없다**는 것이다.

**본 과제 팀이 자체 큐레이션 과정에서 직접 확인한 실증 사례 (FACTBASE B-2):**

| # | 관측된 현상 | 정부 원장 대조 결과 | 조치 |
|---|---|---|---|
| 1 | 웹 검색 상위 노출 업체가 **업계 최저 수준 MOQ(300개)** 를 광고 | **식약처 화장품제조업 등록이 존재하지 않음** | 검증 배지 **부여 거부** |
| 2 | 자사를 "제조사"로 소개한 업체 | 원장에는 **`화장품책임판매`만 등록** = 브랜드/유통사이지 **공장이 아님** | 중개상으로 분류 |
| 3 | 영어권 검색 상위 노출 업체 **다수** | 남의 공장을 재판매하는 **소싱 에이전시** | 중개상으로 분류 |

**이 현상의 구조적 원인 — 원장 통계로 확인되는 사실:**

| 기준 | 등록 회사 수 | 그중 **`화장품제조`**(공장) | 제조업 비중 |
|---|---|---|---|
| **사업자등록번호 기준 (회사 수)** | **28,237곳** | **4,115곳** | **14.6%** |

> **즉, 식약처에 화장품 업체로 등록된 회사 28,237곳 중 실제 제조 시설을 보유한 곳은 4,115곳(14.6%)뿐이며, 나머지 85.4%는 `화장품책임판매`(브랜드/유통)로 공장이 아니다.**
>
> ※ **산출 기준(중요)**: 사업자등록번호 기준 **회사 수**로 산출하였다. 원장의 **등록 행(row) 기준**(32,109행 중 제조 4,120행 = 12.8%)은 **중복 계산**이므로 쓰지 않았다 — 제조사는 통상 `화장품제조`와 `화장품책임판매` 양쪽에 모두 등록되어 한 회사가 두 번 집계되기 때문이다.
> ※ 산출식: `SELECT count(DISTINCT bizrno), count(DISTINCT bizrno) FILTER (WHERE induty='화장품제조') FROM kr_cosmetics_firms` (자사 적재 식약처 원장, 2026-07-13 실측)

웹에서 "Korean cosmetics manufacturer"를 표방하는 주체 중 **압도적 다수가 통계적으로 공장이 아닐 수밖에 없는 모집단 구조**이며, AI는 웹 텍스트를 학습·검색하므로 **이 왜곡을 그대로 증폭**한다. 이것이 본 과제가 해결하려는 기술 문제다.

**해외 바이어가 실제로 입는 피해 (문제의 결과):**

| 피해 유형 | 내용 |
|---|---|
| 마진 손실 | 중개상을 공장으로 오인 → 불필요한 중간 마진 지불 |
| 품질 통제 불가 | 실제 생산 주체를 모름 → 클레임 대응 불가 |
| 선금 손실 | **이미 폐업한 업체**에 선금 송금 |
| 인증 허위 | 근거 없는 "GMP 보유" 주장을 검증할 수단 없음 |

### 1-2-3. 왜 "AI 성능 개선"이 아니라 "검증 레이어"인가

| 접근 | 한계 |
|---|---|
| 더 좋은 LLM 사용 | 환각 확률을 낮출 뿐, **0으로 만들지 못함**. 게다가 "이 회사가 공장인가"는 **모델 능력의 문제가 아니라 법적 등록 사실의 문제**이므로 LLM 내부에 답이 없다. |
| 웹 크롤링 강화 | 크롤링 대상인 웹 자체가 왜곡 소스(1-2-2 참조). 쓰레기를 더 많이 모을 뿐. |
| 사람이 검수 | 확장 불가 (인건비 선형 증가), 본 사업의 자동화 전제와 충돌 |
| **정부 원장 대조 (본 과제)** | **법적 등록 사실이라는 결정적 진실 기준**에 대조. AI의 성능과 무관하게 **거짓 주장을 구조적으로 차단**. |

> **핵심 기술 명제**: *"AI 환각은 더 똑똑한 모델로 줄이는 것이 아니라, 검증 가능한 외부 원장(ground truth)에 강제로 대조시켜 구조적으로 차단해야 한다."*
> 본 과제는 이 명제를 **한국 정부 인허가 공공데이터**라는 구체적 원장 위에서 구현·고도화한다.

## 1-3. 국내외 기술 동향 및 경쟁기술과의 비교

### 1-3-1. 기술 동향

| 동향 | 내용 | 본 과제와의 관계 |
|---|---|---|
| **LLM 그라운딩(Grounding)/RAG 확산** | 생성형 AI의 환각을 줄이기 위해 외부 문서·검색 결과를 근거로 제시하는 기법이 표준화 | 본 과제는 그라운딩 소스를 **"웹 문서"가 아니라 "정부 인허가 원장"** 으로 격상. 웹 그라운딩은 여전히 웹의 왜곡을 상속하므로 불충분 |
| **공공데이터 개방 확대** | 식약처·국세청 등 인허가·사업자 상태 데이터의 API 개방 | 본 과제의 물리적 전제. 6종 원장 + 실시간 사업자 상태 API를 이미 적재·연동 완료 |
| **B2B 소싱의 AI화** | 소싱 프로세스에 AI 챗봇/추천 도입 시도 증가 | 대부분 **추천 단계까지만 AI화**하고 **검증은 여전히 사용자에게 위임**. 본 과제의 공백 지점 |
| **공급망 실사(Due Diligence) 규제 강화** | 공급망 투명성 요구 증가 | "누가 실제 제조 주체인가"의 기계적 판별 수요 증가 |

### 1-3-2. 경쟁기술 비교

> ※ 특정 경쟁사 실명은 단정적으로 기재하지 않고, **기술 유형(type)** 으로 비교한다.

| 비교 축 | ① 일반적인 AI 소싱 도구 / LLM 챗봇 | ② 기존 B2B 디렉토리 / 마켓플레이스 | ③ 소싱 에이전시 (인력 기반) | ④ **GloSource AI (본 과제)** |
|---|---|---|---|---|
| **AI 기반 공급사 후보 추천** | **O** | ✕ (검색·필터 방식) | ✕ (담당자 경험) | **O** |
| **정부 인허가 원장 교차검증** | **✕** | **✕** (업체 자기신고 정보 게재) | △ (담당자가 수동 확인, 비공개) | **O — 6종 원장 + 실시간 API** |
| **제조사 vs 중개상 판별** | **✕** | **✕** (양쪽 모두 "supplier"로 게재) | △ (알지만 **밝힐 유인이 없음**) | **O — `화장품제조` vs `화장품책임판매` 등 등록업종 코드로 판별** |
| **실시간 폐업/휴업 확인** | **✕** | ✕ (원장 갱신 지연) | ✕ | **O — 국세청 사업자 상태 실시간 API** |
| **검증 불가 영역의 명시** | ✕ (그럴듯하게 서술) | ✕ | ✕ | **O — "검증 불가" 명시적 출력** (예: 의류) |
| **응답 속도** | 즉시 | 즉시 | 수일~수주 | **90초 이내** |
| **이해상충** | 낮음 | **광고/입점비 모델 → 상위 노출 왜곡 유인** | **높음 — 중개 수수료가 수익원** | **없음 — 구독료 모델, 거래 미개입** |
| **확장성** | 높음 | 높음 | **낮음 (인력 선형 투입)** | 높음 |

### 1-3-3. 비교 결과 — 기술적 공백(Gap)

세 유형 모두 **"AI가 뱉은 후보 / 업체가 자기신고한 정보 / 사람이 아는 정보"** 를 최종 답으로 제시하며, **국가가 보유한 법적 등록 사실과 기계적으로 대조하는 단계가 부재**하다.

> **본 과제의 기술적 포지션**: 위 유형들과 경쟁하는 것이 아니라, **그들 모두가 생략한 "검증 게이트"를 기술로 구현**한다. 이는 대체 가능한 기능 개선이 아니라 **누락된 아키텍처 계층의 신설**이다.

### 2-2-3. 지표 설정의 근거 및 한계 (정직성 선언)

| 항목 | 서술 |
|---|---|
| **"미측정"의 의미** | 지표 1·4·5는 **기능이 동작하지 않는다는 뜻이 아니라, 정량 측정 프로토콜과 라벨링 평가셋이 아직 없다는 뜻**이다. 해당 기능은 이미 프로덕션에서 동작 중이다. **본 과제의 첫 단계가 이 측정 체계 수립이다.** |

| **평가 기관** | 공인시험기관을 통한 제3자 검증을 원칙으로 하되, 소프트웨어 알고리즘 정확도에 대한 적정 시험기관 선정은 **【확보 필요】** 이며, 최소한 **재현 가능한 측정 스크립트 + 원시 로그**를 산출물로 제출한다. |

## 2-3. 개발 내용 (세부 개발항목)

### ■ 개발항목 1. 공공데이터 레지스트리 통합 적재 파이프라인 확장

| 구분 | 내용 |
|---|---|
| **현재 상태 (선행 실적)** | 6종 원장(화장품·CGMP·HACCP·의료기기·건강기능식품·의약외품) + 국세청 실시간 사업자 상태 API를 이미 적재·연동하여 **프로덕션에서 대조 동작 중** |
| **해결할 기술 문제** | **HACCP 인증만으로는 "진짜 공장"인지 판별할 수 없다.**<br>HACCP은 **식품 안전관리 인증**이지 **제조업 허가 자체가 아니다.** 따라서 현재 K-Food 카테고리는 "HACCP 원장에 존재함"까지만 확인할 뿐, 해당 업체가 **`식품제조·가공업`(공장)** 인지 **`유통전문판매업`(제조를 위탁하고 유통만 하는 브랜드)** 인지 구분하지 못한다.<br>→ **화장품에서 해결한 `제조 vs 책임판매` 판별을, 식품에서도 동일하게 구현해야 한다.** |
| **개발 내용** | ① **식품 인허가 원장(식품제조가공업/유통전문판매업 등 업종 구분 포함) 신규 적재**<br>② 원장별 상이한 스키마·갱신주기·식별자 체계를 흡수하는 **정규화 스키마(canonical registry schema)** 설계<br>③ 원장 추가 시 코드 수정 없이 등록 가능한 **어댑터(Adapter) 구조** — API 정책 변경 리스크 완화의 기술적 근거<br>④ 증분 동기화(delta sync) 및 적재 실패 시 **롤백·재시도 파이프라인**<br>⑤ 카테고리별 **"업종 코드 → 제조/유통 판정" 매핑 테이블**을 코드가 아닌 **선언적 규칙(declarative rule)** 으로 외부화 |
| **핵심 산출물** | 확장 레지스트리 파이프라인 · 정규화 스키마 문서 · 업종코드 판정 규칙셋 · 적재 검증 리포트 |
| **관련 성능지표** | 지표 2 (원장 커버리지 6종 → 9종 이상), 지표 6 (적재 레코드 수), 지표 8 (검증 가능 카테고리) |

### ■ 개발항목 2. 사업자등록번호 기반 정밀 매칭 엔진

| 구분 | 내용 |
|---|---|
| **현재 상태 (선행 실적)** | 회사명(상호) 문자열 매칭 + 사업자등록번호 매칭을 병용. 큐레이션 공급사 **26건 중 16건(61.5%)** 이 사업자등록번호 보유 |
| **해결할 기술 문제 (실증됨)** | **회사명 문자열 매칭은 구조적으로 실패한다.**<br>정부 인허가 원장은 다수의 경우 **공장(사업장) 단위로 등재**되는 반면, 웹에 노출되는 이름은 **본사·브랜드명**이다. 따라서:<br>· 본사명으로 원장을 조회하면 **매칭 실패**(실제로는 등록된 제조사인데 "미등록"으로 오판) → **거짓 음성(False Negative)**<br>· 유사 상호(예: "○○코스메틱" vs "○○코스메틱스")로 **다른 법인에 잘못 매칭** → **거짓 양성(False Positive)**<br>→ **사업자등록번호(고유 식별자) 기반 1:1 정밀 매칭이 유일한 근본 해법이다.** |
| **개발 내용** | ① **사업자등록번호를 1차 키(primary key)** 로 하는 매칭 엔진 재설계 — 상호 매칭은 **후보 축소용 보조 신호로 강등**<br>② 사업자번호 미보유 후보에 대한 **번호 보강(enrichment) 파이프라인**: 공개 원장 역참조 + 웹 공개 정보(사업자정보 표기 의무 페이지) 추출 → **번호 후보 생성 후 국세청 API로 유효성 검증**<br>③ **본사–공장(사업장) 관계 해소 로직**: 동일 사업자번호 하위 복수 사업장, 법인 상호 변경 이력 처리<br>④ 매칭 결과에 **신뢰도(confidence) 등급** 부여 — 사업자번호 정확일치 / 상호+주소 복합일치 / 상호 단독(약함) / 매칭 실패<br>⑤ **매칭 실패를 "미등록"으로 오판하지 않도록** 판정 상태를 3분류(등록확인 / 미등록확인 / **판별불가**)로 분리 |
| **핵심 산출물** | 사업자번호 기반 매칭 엔진 · 번호 보강 파이프라인 · 신뢰도 등급 규칙 · 매칭 정확도 실측 리포트 |
| **관련 성능지표** | 지표 1 (제조사–중개상 판별 정확도), 지표 3 (사업자번호 정밀 매칭률 61.5% → 90% 목표) |

> **기술적 의의**: 3분류 판정(등록확인/미등록확인/**판별불가**)은 단순한 UX 개선이 아니다. **"매칭 실패"와 "미등록"을 구분하지 못하면 정직한 검증 시스템이 성립하지 않는다.** 이 구분이 본 과제의 신뢰성 설계 핵심이다.

### ■ 개발항목 3. AI 환각 차단 검증 레이어 (Hallucination Guard)

| 구분 | 내용 |
|---|---|
| **현재 상태 (선행 실적)** | 큐레이션 데이터에 대한 **"정직성 불변식(honesty invariant) 테스트"** 를 구현하여 **근거 없는 인증 주장·조작된 신뢰 점수·미검증 공급사를 차단**하고 있으며, 이 테스트는 **자동 배포 게이트에서 실행**되어 위반 시 배포가 차단된다. |
| **해결할 기술 문제** | 현재는 **큐레이션 데이터(정적)** 에 대한 불변식 검사에 머물러 있다. **AI가 실시간 생성하는 동적 응답**에 대해서도 동일한 강도의 차단이 필요하다. LLM은 다음을 자연스럽게 지어낸다:<br>· 존재하지 않는 인증 보유 주장 ("ISO 22716 certified")<br>· 원장에 근거 없는 제조 능력 주장<br>· 근거 없이 높은 신뢰 점수<br>· 실재하지 않는 업체 (완전 환각) |
| **개발 내용** | ① **주장(claim) 추출기**: AI 응답에서 **검증 가능한 사실 주장**(제조업 등록, 인증 보유, 사업자 상태)을 구조화 추출<br>② **근거 요구 규칙(evidence-required rule)**: 모든 사실 주장은 **정부 원장 레코드 ID를 근거로 첨부해야만 출력 허용**. 근거 없는 주장은 **출력 자체에서 제거**(soft-fail이 아닌 **hard-block**)<br>③ **신뢰 점수 산식의 검증 가능화**: 점수를 LLM이 생성하지 않고, **원장 대조 결과로부터 결정론적으로 계산**하여 조작 자체를 불가능하게 함<br>④ **레드팀 평가셋 구축(≥ 200 케이스)**: 허위 인증·허위 등록·조작 점수·존재하지 않는 업체를 의도적으로 주입하여 차단률 실측<br>⑤ 불변식 테스트를 **정적 큐레이션 → 실시간 응답 경로**로 확대 적용 |
| **핵심 산출물** | 주장 추출기 · 근거 요구 규칙 엔진 · 결정론적 점수 산식 · 레드팀 평가셋 · 차단률 실측 리포트 |
| **관련 성능지표** | 지표 5 (AI 환각 주장 차단률), 지표 9 (회귀 테스트 34건 → 100건 이상) |

> **본 항목이 과제의 기술적 정체성이다.** "AI로 공급사를 찾아준다"는 기술적 난이도가 낮고 차별성이 없다. **"AI가 지어낸 말을 정부 원장으로 구조적으로 차단한다"** 가 본 과제가 주장하는 신규성이다.

### ■ 개발항목 4. 실시간 사업자 상태(폐업/휴업) 감시 및 경보

| 구분 | 내용 |
|---|---|
| **현재 상태 (선행 실적)** | **국세청 사업자 상태 실시간 API 연동 완료** — 계속사업자 / 휴업 / 폐업 조회 동작. 폐업·휴업 업체는 검증 배지 대신 **경고 표시**. 공급사 URL 생존 검증(죽은 링크 → 신뢰도 강등)도 동작 중. |
| **해결할 기술 문제** | 현재는 **조회 시점(on-demand) 확인**에 가깝다. 그러나 실제 피해는 **"바이어가 조회한 이후, 송금 이전"** 구간에서 발생한다. 또한 이미 리포트를 받아간 사용자는 **해당 공급사가 그 후 폐업해도 알 수 없다.** → **상태 변경을 능동 감시하고 소급 경보하는 구조**가 필요하다. |
| **개발 내용** | ① **상태 변경 감시 스케줄러**: 리포트에 포함된 적이 있는 전체 공급사를 주기적 재조회 (감지 지연 **≤ 24시간** 목표)<br>② **소급 경보(retroactive alert)**: 사용자가 이전에 조회했던 공급사의 상태가 **계속사업자 → 휴업/폐업**으로 변경 시 해당 사용자에게 이메일 경보 발송<br>③ **API 레이트리밋·장애 대응**: 국세청 API 호출량 제어, 캐시 계층(TTL), 장애 시 **"최근 확인 시각"을 명시하고 낙관적 판정을 하지 않음** (장애 시 "확인됨"으로 표시 금지)<br>④ **위험 신호(red flag) 통합**: 폐업/휴업 + URL 사망 + 제조업 미등록 + 인증 근거 부재를 **단일 위험 프로파일**로 통합 산출<br>⑤ 상태 이력 보존(감사 추적) — 언제 어떤 근거로 어떤 판정을 내렸는지 재현 가능 |
| **핵심 산출물** | 감시 스케줄러 · 소급 경보 파이프라인 · 캐시/레이트리밋 계층 · 위험 프로파일 산출기 · 상태 이력 감사 로그 |
| **관련 성능지표** | 지표 4 (폐업/휴업 탐지 재현율, 감지 지연 ≤ 24h) |

## 2-4. 기술성숙도 (TRL)

> ⚠ 본 과제는 **아이디어 단계가 아니다.** 검증 엔진이 **프로덕션에서 실동작 중**이며 라이브 서비스가 배포되어 있다(`GET /en` HTTP 200). TRL을 과소 기재하지 않는다.

|---|---|---|
